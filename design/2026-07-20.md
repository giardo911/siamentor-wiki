# 2026-07-20 — Stale proof recovery after deleted memory

## Фокус дня

`stale_proof_recovery_after_forget`: если пользователь нажал `Забыть` для receipt, а затем пытается открыть старый proof/paywall entrypoint, продукт должен не продавать подписку на устаревшем доказательстве, а вернуть его в короткое новое действие по той же книге.

## Проблема

После удаления памяти цепочка `книга -> действие -> привычка` становится неполной: старое действие больше нельзя использовать как proof evidence. Если при этом старый CTA или deep link ведет на paywall, пользователь видит давление "заплати за прогресс", который он только что попросил забыть. Это ломает trust boundary и делает privacy-control декоративным.

## Дизайн-решение

Ввести состояние `stale_proof_recovery_after_forget` для consumer mobile flow:

- оставить видимым book/thesis anchor: книга и выбранная идея не удаляются;
- явно показать proof reset `0/3 проверенных действий`;
- заблокировать старый paid CTA до нового verified/corrected receipt;
- предложить новое действие на 3-5 минут без удаленного trigger/friction;
- после выполнения создать pending receipt и вернуть пользователя в обычный review gate.

Это не экран ошибки и не LMS-страница прогресса. Это короткий восстановительный экран: "мы уважаем удаление, но можем начать заново от идеи книги".

## Ключевые состояния

- `forgotten_receipt`: receipt удален, proof eligibility пересчитан, old receipt excluded.
- `stale_proof_entrypoint`: пользователь пришел со старого CTA, пуша, bookmark или `/habits/proof`.
- `stale_proof_recovery_after_forget`: paywall скрыт, proof `0/3`, показано новое действие <=5 минут.
- `new_action_completed_after_forget`: создан новый pending receipt без deleted memory.
- `review_new_receipt`: пользователь подтверждает/исправляет/забывает новый receipt перед следующим действием.

## Открытые вопросы

- Нужен ли отдельный event для попытки открыть stale paywall: `stale_proof_entrypoint_blocked`?
- Показывать ли пользователю название удаленного receipt в обезличенном виде (`прошлое действие забыто`) или вообще не напоминать о нем?
- Должен ли новый action быть строго template-first без LLM, чтобы privacy reset не порождал лишний AI-context?

## Acceptance contract

Product spec name: `habit-stale-proof-recovery-after-forget.spec.ts`

Scenario:

1. User has a proof-ready state with 3 verified receipts and a visible paid CTA.
2. User clicks `Забыть` on one receipt.
3. Product records `habit_memory_deleted_by_user`, recomputes proof progress to `0/3` or to the verified count that excludes the deleted receipt, and stores a stale proof blocker.
4. User opens the old proof entrypoint (`/ru/habits/proof`, old CTA, push, bookmark).
5. Product must show `stale_proof_recovery_after_forget`, not the paid proof paywall.
6. The recovery state keeps book/thesis anchor visible, hides or disables paid CTA, and says the old proof is no longer used.
7. The user receives a template-first action <=5 minutes that does not reuse deleted `completed_action`, `trigger`, or `friction`.
8. Clicking `Сделал` creates a new pending receipt and returns the user to the normal receipt review gate before any proof/paywall eligibility.

Required assertions:

- `trial_started_from_stale_proof` is never emitted.
- `stale_proof_entrypoint_blocked` is emitted with `deleted_receipt_excluded=true`.
- `forgotten_receipt_rebuild_shown` is emitted with `proof_progress_after_forget=0` or the corrected verified count.
- `new_receipt_after_forget_created` is emitted only after the new action completion.
- User-facing copy contains `0/3 проверенных действий`, book title, thesis/idea, action duration `5 минут`, and a disabled paid label `Продолжение откроется после 3 проверенных действий`.

Implementation notes:

- Reuse the existing `forgotten_receipt_rebuild` state where possible; this task adds the stale entrypoint guard, not a second recovery surface.
- Prefer deterministic template action. LLM may be used later only for `shrink/clarify/rewrite`, and must not receive deleted receipt content.
- Proof eligibility should be derived from current verified/corrected receipts, never from cached proof page state.
