# 2026-07-12 — Offline fallback action после verified memory

## Фокус дня

Состояние `offline_verified_memory_action`: пользователь возвращается на Day 2-7 без сети или при LLM timeout, но у продукта уже есть verified/corrected memory receipt: книга, цель, trigger, friction и последнее выполненное действие.

## Проблема

Book-to-habit loop не должен ломаться из-за сетевого сбоя или дорогого LLM fallback. Если после verified receipt экран показывает generic error, spinner или предлагает "попробовать позже", цепочка книга -> действие -> привычка обрывается прямо перед daily action. Это ухудшает D7 retention и скрывает cost-risk: пользователь не видит ценность, а продукт тратит LLM-вызовы на восстановление того, что уже известно из memory receipt.

## Дизайн-решение

Mobile-first экран строит следующий микро-шаг локально из verified memory:

1. Сверху короткий receipt: "Помню: ты применяешь `<book_thesis>` через `<trigger>`".
2. Ниже один offline action <=5 минут, собранный template-first из последнего completed action и friction.
3. Primary CTA: "Сделал".
4. Secondary CTA: "Изменить шаг".
5. Network badge не пугает: "Можно выполнить без сети. Синхронизируем позже".

LLM не блокирует действие. Когда сеть вернется, продукт отправляет completion receipt и может уточнить следующий шаг, но текущая привычка уже продолжилась.

## Ключевые состояния

- `offline_action_ready`: есть verified receipt, сеть недоступна, показан локальный action <=5 минут.
- `offline_action_completed_pending_sync`: пользователь нажал "Сделал"; progress локально меняется на `N/3`, receipt ожидает sync.
- `sync_success_receipt_verified`: completion отправлен, chain сохранена, следующий день продолжает habit.
- `sync_conflict_memory_changed`: если пользователь на другом устройстве исправил memory, показываем diff и предлагаем оставить последний verified trigger.
- `no_verified_memory_fallback`: если receipt не verified/corrected, offline mode показывает только safe retry и не выдумывает action.

## UX-copy

- Receipt: "Помню из вчера: книга -> маленькое действие -> триггер."
- Offline badge: "Без сети, но шаг можно сделать сейчас."
- Action title: "5 минут: повтори следующий шаг"
- Action body: "После `<trigger>` сделай `<micro_action>`. Если помешает `<friction>`, уменьши шаг до 2 минут."
- Completed receipt: "Готово. Засчитаем прогресс после синхронизации."
- No-memory fallback: "Нужна сеть, чтобы не придумать шаг без твоего подтверждения."

## Открытые вопросы

- Должен ли pending sync засчитываться в paywall proof сразу или только после server receipt?
- Как долго хранить offline completion до обязательного sync: 24 часа или до следующего открытия?
- Нужно ли показывать cost/debug метку для internal build: `template_fallback_used=false`, `llm_calls=0`?
- Как защититься от двойного completion, если пользователь нажал "Сделал" offline и online на другом устройстве?

## Acceptance notes

- Action всегда связан с конкретной книгой и verified memory, а не с generic motivation.
- В free-to-paywall path offline completion может стать одним из proof actions, но paywall copy обязан явно показывать pending/verified статус.
- Метрики: `offline_habit_action_shown`, `offline_action_completed_pending_sync`, `offline_completion_synced`, `offline_completion_conflict`, `llm_calls_per_completed_action`.
